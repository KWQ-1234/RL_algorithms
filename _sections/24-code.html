Reading real code: one loss function, a handful of config flags

The skeleton's three slots exist in code as a handful of functions and configuration flags. Reading them is the fastest way to check what a run actually computed, because the defaults of a framework are often not the method a paper describes. This section reads verl's policy loss against the axes. The excerpts are trimmed for the argument; the comments give the line numbers in verl at commit 7dc39fe (May 2026), where the full code can be checked.

The surrogate: one function, four regions

verl: verl/trainer/ppo/core_algos.py· compute_policy_loss_vanilla, lines 1329–1361 
negative_approx_kl = log_prob - old_log_prob
negative_approx_kl = torch.clamp(negative_approx_kl, min=-20.0, max=20.0)
ratio = torch.exp(negative_approx_kl)                               # r = π_θ / π_old
pg_losses1 = -advantages * ratio
pg_losses2 = -advantages * torch.clamp(ratio, 1 - cliprange_low, 1 + cliprange_high)
clip_pg_losses1 = torch.maximum(pg_losses1, pg_losses2)            # PPO-clip
pg_losses3 = -advantages * clip_ratio_c
clip_pg_losses2 = torch.min(pg_losses3, clip_pg_losses1)
pg_losses = torch.where(advantages < 0, clip_pg_losses2, clip_pg_losses1)  # dual-clip
if rollout_is_weights is not None:
    pg_losses = pg_losses * rollout_is_weights                       # gap-1 correction
pg_loss = agg_loss(loss_mat=pg_losses, loss_mask=response_mask, loss_agg_mode=loss_agg_mode, ...)

The goal of the first block is the PPO surrogate of axis ④. The loss is the negative of min(rÂ, clip(r)Â), written as a maximum of negatives, which is where the mask of Figure 5 comes from: once the clipped branch is the larger loss, its gradient with respect to the parameters is zero. cliprange_low and cliprange_high are separate, which is how clip-higher enters. The second block is dual-clip, and the torch.where applies it only where the advantage is negative — the bottom-right quadrant of Figure 5, where a bad token's probability has risen and its weight r would otherwise be unbounded. The third block multiplies by importance weights computed from the sampler's log-probabilities when rollout correction is enabled: the only line in the function that can see gap 1 of axis ⑥. If old_log_prob is recomputed on the trainer and there is one step per batch, ratio is 1 here, neither the clip nor the dual-clip branch is active, and the loss reduces to −Â · ratio with gradient −Â ∇log π (r ≡ 1).

The normalizer: four aggregation modes

verl: verl/trainer/ppo/core_algos.py· agg_loss, lines 1168–1195 
if loss_agg_mode == "token-mean":
    loss = verl_F.masked_sum(loss_mat, loss_mask) / batch_num_tokens * dp_size
elif loss_agg_mode in ["seq-mean-token-sum", "seq-mean-token-sum-norm"]:
    seq_losses = torch.sum(loss_mat * loss_mask, dim=-1)              # sum over a response
    loss = verl_F.masked_sum(seq_losses, seq_mask) / global_batch_size * dp_size
    if loss_agg_mode == "seq-mean-token-sum-norm":
        if loss_scale_factor is None:
            loss_scale_factor = loss_mask.shape[-1]                   # "constant" divisor
        loss /= loss_scale_factor
elif loss_agg_mode == "seq-mean-token-mean":
    seq_losses = torch.sum(loss_mat * loss_mask, dim=-1) / (seq_mask + 1e-8)   # ÷ |y_i|
    loss = verl_F.masked_sum(seq_losses, seq_mask) / global_batch_size * dp_size

These are the rows of axis ③'s table. token-mean divides by the number of valid tokens in the PPO mini-batch, summed over data-parallel workers — not per prompt group as in DAPO's formula. seq-mean-token-mean is the original GRPO's 1/|yi| weighting. seq-mean-token-sum-norm is meant to be Dr. GRPO's constant normalizer; by default it divides by the mask's last dimension, which on some code paths is the padded width of the current micro-batch rather than a fixed constant (our reading of the code, not a measured effect).

Read against the decision guide, the stock configuration departs from the recommended defaults in three places: it trains with four optimizer steps per batch, divides by the group standard deviation when GRPO is selected, and leaves mismatch correction off. None of these is wrong for every run, but each is a choice the user inherits without making it. The pitfalls section collects the cases where an inherited default changes the mathematics.
